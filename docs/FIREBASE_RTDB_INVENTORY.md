## 2. Core entity detail

### 2.1 `restaurants/$restId/orders/$pushId` — 59 records, 3 restaurants

| Aspect | Finding |
|---|---|
| Purpose | Every customer order: dine-in, delivery, takeaway |
| Producers | `client.js`, `waiter.js`, `kassa.js`, `chef.js`, `admin.js`, `paymentEngine.js`, `orderActions.js` |
| Consumers | Every panel; `chef.js` listens with `limitToLast(500)`, `admin.js` with `limitToLast(300)` |
| Key format | 100% Firebase push ids |
| Timestamps | Epoch **milliseconds** as numbers (`Date.now()`); no `serverTimestamp()` anywhere |
| Reader roles | admin, waiter, cashier, chef, courier, client (own order) |
| Writer roles | admin, waiter, cashier, chef, client (create) |

**Fields (fill rate from 29 sampled records):**

| Field | Fill | Type | Notes |
|---|---|---|---|
| `createdAt` | 100% | number | epoch ms |
| `status` | 100% | string | **mixed Uzbek/English** |
| `statusKey` | 100% | string | machine key |
| `statusLabel` | 100% | string | localized display |
| `statusHistory` | 100% | object | keyed **by status name** → timestamp |
| `total`, `originalTotal`, `discount` | 100% | number | money |
| `orderNumber` | 100% | number | from `meta/orderCounter*` |
| `clientId` | 100% | string | `waiter_…` or `CL_<uuid>` |
| `items` | 96.6% | object | keyed `{menuId}__{ts}` |
| `updatedAt` | 86.2% | number | |
| `payment` | 82.8% | object | `{paid, method, paidAt, kassir, finalTotal, serviceFeeAmount, …}` |
| `statusV2` | 79.3% | string | newer machine key |
| `customerId`/`customerPhone` | 65.5% | string | **the phone number itself** |
| `table` | 62.1% | **string** | `"4"`, not a number |
| `waiterId` | 62.1% | string | `waiter_…` |
| `orderType` | 48.3% | string | `delivery`/`dine_in` |
| `deliveryAddress` | 41.4% | **object \| string** | **polymorphic** |

**Migration problems:**

1. **Four competing status fields** → resolved by documented precedence, all
   raw values retained. See `STATUS_MIGRATION_MAP.md`.
2. **`deliveryAddress` is `object|string`** → stored as `jsonb`, both shapes
   preserved.
3. **`table` is a string** → `table_label` keeps the raw value; `table_id` is
   the resolved FK, nullable.
4. **`orderType` missing on 45/59** → inferred only from positive in-record
   evidence (`table` present ⇒ dine-in, `deliveryAddress`/`isDelivery` ⇒
   delivery), otherwise `unknown`. Every inference is reported.
5. **Order numbers repeat across types** — two counters (`orderCounterOrd`,
   `orderCounterDvr`) → unique per `(restaurant, type, number)`.
6. **Redundant flags**: `isDelivery`/`deliveryType`/`orderType` and
   `notified`/`isNotified` can disagree.

### 2.2 `orders/$orderId/items/$compositeKey` — 147 records

Key is `{menuItemId}__{timestampMs}` (or `combo_{id}__{ts}`, or bare
`combo_{id}`), so the same dish added twice yields two entries. **The
composite key is the item's identity** and becomes `legacy_rtdb_id`.

Fields: `name`, `price`, `qty`, `status`, `kitchenStatus`, `modifiers`,
`extras`, `isCombo`. **No `total` field exists on any item** — the line total
is computed at render time, so the migration computes `price × qty` and
reports every instance (147/147).

These are **historical snapshots** (`name_snapshot`, `price_snapshot`) and are
never re-derived from `menu_items`.

### 2.3 `orders/$orderId/statusHistory` — 138 records

An object keyed **by status name**, value = timestamp. Child keys observed:
`order_created`, `preparing`, `picked_up`, `served`, `payment`, `completed`.
**Three of those (`preparing`, `picked_up`, `payment`) appear in no status
field**, making this tree a genuine source of states the order record alone
does not reveal.

### 2.4 `restaurants/$restId/customers/$phoneKey` — 8 records

**Keys are phone numbers** (8/8 phone-shaped), and the record's own `id`
field repeats the phone. Requirement #7 forbids phone as the PK.

Notable fields: `personalDiscount`, `personalDiscountSource`
(`receipt_qr` / `customers_module`), `totalSpent` (max 1,364,581.5),
`visits`, `loyaltyCard {cardNumber, createdAt, enabled}`, `orderIds`
(a set of order ids), `savedAddresses` (push-keyed → own table).

`orderIds` is **not** migrated as a column — it is derivable from
`orders.customer_id`, and storing it twice invites divergence.

### 2.5 `restaurants/$restId/users/$userId` — 85 records, 43 restaurants

Keys are `{role}_{timestamp}` prefixed ids. Contains the **role corruption**
documented in `STATUS_MIGRATION_MAP.md` §6: 3 records with `role: ""` and 1
with a `customRoleId` push id in the `role` field.

Also carries duplicated pay fields: `serviceBonus` (string, `"%5"`) and
`serviceFeePercent` (number, `5`).

### 2.6 `credentials/$restId/$userId`

Password material, deliberately separate from `users`. Fields include
`password` and `passwordEnc`. **Never sampled into any report** — the
discovery script redacts this subtree's values.

## 4. Structural problems carried into the schema

### 4.1 `inventory` and `ingredients` are a dual-write pair

Both hold 13 records across the same 3 restaurants, with identical field
profiles (`unit` ∈ {kg, gr, dona}, `price` 4–200,000, `stock` 0–300). Nearly
every application write to one is mirrored to the other.

**Decision:** one table, `inventory_items`, with a `tracked_as` column
recording which tree(s) a row came from. Two tables would institutionalize a
bug; one table plus provenance preserves the fact without the duplication.
The migration reports any pair whose values actually disagreed.

### 4.2 Three overlapping audit trees

| Tree | Writer | Records |
|---|---|---|
| `auditLog` | backend `auditLog.js` | 32 |
| `audit_log` | frontend `admin.js` | 3 |
| `activityLogs` | operational UI | 658 |

`auditLog` + `audit_log` → one `audit_log` table with a `source_tree` column.
`activityLogs` stays separate: it is a user-facing feed, not a security
trail, and merging them would corrupt both.

### 4.3 Order counters are `runTransaction` increments

`meta/orderCounterOrd` and `meta/orderCounterDvr`. These do not migrate as
data — in PostgreSQL the equivalent is a sequence or a `SELECT … FOR UPDATE`
on a per-restaurant counter row, which is Phase 2's concern. The **current
values** matter only so Phase 2 does not reissue existing numbers.

### 4.4 Concurrency guards that become constraints

Every `runTransaction` site is hand-rolled concurrency control that the
database should own:

| RTDB transaction | PostgreSQL equivalent |
|---|---|
| `reservationSlots/{date}_{time}_{table}` | `UNIQUE (restaurant_id, slot_date, slot_time, table_number)` |
| `orders/$id/payment/paid` false→true | `payments.paid` + row lock |
| `orders/$id/inventoryDeducted` | `orders.inventory_deducted` boolean |
| `orders/$id/chefScoreAwarded` | `orders.chef_score_awarded` boolean |
| `inventory/$id/stock` | `stock_movements` ledger + `SELECT … FOR UPDATE` |
| `dailyUsage/$dateKey/$ingId` | `UNIQUE (restaurant_id, usage_date, legacy_item_id)` |
| `discountClaims/$restId/$token` | `UNIQUE (restaurant_id, token)` + `usage_count` |

### 4.5 No `serverTimestamp()` anywhere

Every timestamp is a client-side `Date.now()`. Combined with the future-dated
`restaurants_meta` record (2027-08-10), this means **timestamps cannot be
fully trusted**. The migration accepts 2015-01-01 … 2035-01-01 and rejects
anything outside, reporting it rather than silently storing a bad date.
